# Review findings — lock (confirmed by an adversarial verifier)

## 1. [high] A Keychain read error counts as 'no PIN set', so any 6 digits unlock Silicon Mode

**Verifier evidence:** Confirmed. PinVault.swift:60 has `guard let rec = try? store.load() else { return .notSet }`. KeychainPinStore.load (lines 133-136) returns nil only for errSecItemNotFound. Every other status hits `guard s == errSecSuccess ... else { throw PinError.storage(s) }`, and a decode failure also throws, so `try?` turns all of them into `.notSet`. The `.notSet` return comes before `failures += 1`, so a read error never counts toward the throttle. Both callers then unlock. AppModel.swift:219 has `case .notSet: handle(.unlocked)`. UnlockView.swift:473-476 has `case .ok, .notSet: await playSuccess(); switch model.unlock(pin: entered) { case .ok, .notSet: break`. ModeEngine `.unlocked` does `guard phase.isActive ... return exit(.unlocked)`, which exits without any further check. The item is a legacy login-keychain item: there is no kSecUseDataProtectionKeychain in `base`. If that keychain is locked (the 'lock after N minutes of inactivity' or 'lock when sleeping' settings, and an overlay left up for hours has no input), SecItemCopyMatching raises the SecurityAgent unlock prompt. Cancel returns errSecUserCanceled, which reads as `.notSet`, and Silicon Mode unlocks. An ACL 'Deny' on a build with a changed signature has the same effect. This requires a non-default keychain setting or a denied prompt, but it is a fail-open in the only auth check, so high is fair. SettingsPin.swift:88 (`case .ok, .notSet: advance(.new)`) has the same flaw, with lower impact because Settings is only reachable while unlocked.

**Fix:** Separate 'no record' from 'read failed'. In verify, write `let rec: Record?; do { rec = try store.load() } catch { return .unavailable }`, then `guard let rec else { return .notSet }`. Add `case unavailable` to VerifyResult. In AppModel.unlock, UnlockView.submit and SettingsPinFlow `.current`, treat `.unavailable` as a failure: show an error, keep Touch ID available, and never call handle(.unlocked). Also, while a session is active, refuse `.notSet` as success when a PIN existed at entry (record `pinWasSet` on `.entered`). Optionally store the item with `kSecUseDataProtectionKeychain: true` to avoid legacy keychain lock state and ACL prompts.

## 2. [high] The kiosk lock is never re-asserted after the app loses focus, and the lock lives only in memory, so Force Quit, kill or a crash ends it

**Verifier evidence:** Confirmed. KioskLock.engage (SystemServices.swift:92-105) registers only a `didBecomeActiveNotification` observer plus a one-shot retry loop, `for delay in [0.15, 0.4, 0.8, 1.5, 3.0, 6.0]`, which ends after about 12 s. Nothing in the app observes didResignActive or didActivateApplication for the kiosk. The only such observers are in MenuBarController (lines 294-300), and they just hide the menu panel. `reassert()` is called only from OverlayController's *local* key and click monitors (lines 298-308), and local monitors only see events delivered to this process. NSApplication presentation options (`.disableProcessSwitching, .disableForceQuit, ...`) apply only while the app is active. So once an agent-launched app takes activation (`open <url>`, a headed browser, the Simulator), keystrokes go to that hidden app and ⌘Tab and ⌥⌘Esc work again, until someone clicks the overlay. The overlay panels are activating (`p.styleMask.remove(.nonactivatingPanel)`), so a click does restore the lock. A keyboard-only attacker can therefore type blind into the agent's Terminal or kill the process. `applicationShouldTerminate` (SiliconModeApp.swift:51-55) only blocks a polite quit. AppModel/ModeEngine phase is memory-only, and no KeepAlive or relaunch mechanism exists: `LoginItem.sync` registers SMAppService.mainApp, which runs only at login. So process death drops the overlay and the lock entirely. One correction: the 'fresh grace minute on relaunch' part is overstated. Nothing relaunches the app after a kill, so the session is simply gone and there is no grace minute. The core bypass stands.

**Fix:** While engaged, observe `NSApplication.didResignActiveNotification` and `NSWorkspace.didActivateApplicationNotification` (pid != own pid) and call `bringForward(); applyIfEngaged()` each time. Also keep a ~1 s watchdog timer while engaged that re-activates whenever `!NSApp.isActive`, instead of stopping after 12 s. To survive a kill or crash, persist a 'locked' marker on `.locked` and clear it only on `.exited(.unlocked)`. Restore a locked session in `AppModel.start()` when the marker exists (via a new engine command), and register a KeepAlive LaunchAgent (SMAppService.agent) while locked so a killed process relaunches straight into the lock.

## 3. [low] The grace minute is timed with systemUptime, which stops during sleep, so a session closed in grace stays unlocked for hours

**Verifier evidence:** The clock behaves as described. AppModel.tick and handle both use `ProcessInfo.processInfo.systemUptime`, which Apple documents as time the system has been awake, so sleep is not counted. ModeEngine.swift:180 locks only `if !act.locked && now - act.enteredAt >= settings.graceSeconds`, and `.systemWillSleep` and `.systemDidWake` do nothing to `locked`. A session entered by lid and put to sleep 20 s later (closing the lid sleeps the Mac even with the PreventUserIdleSystemSleep assertion) wakes with about 40 s of grace left. Lifting the lid then hits line 186, `if !act.locked, !act.manual, let a, a >= threshold + raiseHysteresis ... exit(.lidRaised)`, and the 'Turn off' button also works without the PIN. I am lowering severity: with macOS defaults ('require password immediately after sleep'), the system lock screen appears on wake before anyone reaches the Silicon Mode overlay. A PIN-free exit by someone else is only possible when that macOS setting is relaxed. It is still a real deviation from the 'locked after 1 minute' rule measured in wall-clock time.

**Fix:** Feed the engine a clock that includes sleep, e.g. `Double(clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW_APPROX))`, or better `clock_gettime_nsec_np(CLOCK_MONOTONIC) / 1e9`, which counts sleep on Darwin, or use `mach_continuous_time`. Use it in AppModel.tick, handle and pauseAutoEntry. Alternatively, record `enteredAtWall: Date` in Active and, on `.systemDidWake`, set `locked = true` and emit `.locked` when `Date().timeIntervalSince(enteredAtWall) >= graceSeconds`.

## 4. [medium] 'Pause auto-entry' is timed in uptime but shown in wall-clock time; after sleep, auto-entry stays off while the UI says it has resumed

**Verifier evidence:** Confirmed. AppModel.pauseAutoEntry (lines 228-231) sets `autoPausedUntil = Date().addingTimeInterval(d)` but `handle(.pauseAutoEntry(until: now + d))` with `now = systemUptime`. syncFromEngine (line 204) clears the UI copy by wall clock with `if let p = autoPausedUntil, p <= Date() { autoPausedUntil = nil }`. The engine keeps `pausedUntil` and checks `isAutoEntryPaused(now:)` against uptime (ModeEngine.swift:115-117, 153). Nothing re-syncs on wake: systemDidWake only sends `.systemDidWake`, which leaves `pausedUntil` alone. 'Until Tomorrow' (MenuBarFooter.swift:94, using `untilTomorrowMorning()`, about 9 h at 23:00) almost always spans an overnight sleep. In the morning the UI shows the pause as cleared, the Resume item is hidden (`if let paused` in MenuBarFooter.swift:86), and whyNoEntry (SettingsPanes.swift:509) never names the pause. Meanwhile the engine stays paused for the rest of the slept duration in awake time. Toggling autoEnterEnabled does not reset `pausedUntil` either.

**Fix:** Use one clock. Either drive the engine with a sleep-inclusive monotonic clock (same fix as the grace finding), or keep the pause purely in wall-clock time: store `autoPausedUntil: Date` and in tick call `handle(.pauseAutoEntry(until: nil))` once `autoPausedUntil <= Date()`. On systemDidWake, re-send `.pauseAutoEntry(until: now + autoPausedUntil.timeIntervalSinceNow)` while the pause is still in the future, and send nil when it has passed.

## 5. [low] Panic is not ended before sleep, so the alarm and flashing come back when the Mac is opened later

**Verifier evidence:** Confirmed in code. ModeEngine.swift:228-233: `case .systemWillSleep: if phase.isCountdown { ... } return []`, so `panicSince` survives sleep. AppModel's willSleep handler only calls `handle(.systemWillSleep)`, and SoundPlayer has no sleep observer, so `panicMode` stays `.alarm`. With the lid at about 0° and agents running, none of updatePanic's end conditions fire before sleep: `a >= trigger + 1` is false, `a >= panicSettleMinAngle` is false, and `agentsRunning == 0` is false. On wake, `engineConfigurationChanged()` resumes the loop (`let resume = panicMode == .alarm ? panicLoopName : nil ... g.voice.play(loop: loop, gain: panicGain, fade: 0.03)`), and PanicView stays mounted while `model.isPanicking`. It stops only when the first tick reads the lid above trigger+1 or when didWake delivers `.panicEnded(.settled)`. The replay is short (usually under a second or two), and the strobe is often hidden by the macOS lock screen. It is still audible and contradicts the spec's 'doesn't play anything if the mac was closed and then opened again later'. Low severity is right.

**Fix:** In ModeEngine `handle(.systemWillSleep)`, also end any panic: `if var act = phase.active, act.panicSince != nil { act.panicSince = nil; phase = .active(act); return [.panicEnded(.settled)] }`. In AppModel's willSleep observer, stop the voice immediately rather than with the 250 ms fade, e.g. add `sounds.stopPanic(immediate: true)` that sets `panicMode = .off` and silences the voice at once, so engineConfigurationChanged cannot resume it on wake.

## 6. [low] One failed sensor re-probe turns off lid reading until the next wake, killing panic, lid exit and auto-entry

**Verifier evidence:** Confirmed. AppModel.tick (lines 161-168) reads only `else if sensorAvailability == .available`, and the only in-loop recovery is `if readFailures % 90 == 0 { sensor.probe(); sensorAvailability = sensor.availability }`. LidSensor.probe sets `.vendorInterfaceOnly` or `.notFound` whenever the test read `Self.read(d, openFirst: true)` fails, or when `IOHIDManagerOpen` fails. After that, tick neither reads nor probes, and readFailures is frozen. The only other probe is in `systemDidWake()` (line 248). While the sensor is unavailable the engine gets `angle: nil`, so auto-entry (`guard let a` at line 153) and the grace lid exit both stop working. updatePanic keeps working off the frozen `sampler.latest` and `velocity` (velocity uses only sample timestamps, so a stale closing slope stays 'closing'). The trigger needs the HID device to be unresponsive for 3 s *and* at the probe moment, which is uncommon. The stuck-panic sub-case usually heals, because a closed lid sleeps the Mac and wake re-probes. Low severity is right.

**Fix:** Keep retrying while unavailable. Add a `probeCountdown` and, in tick, run `if simulatedAngle == nil && sensorAvailability != .available { probeCountdown -= 1; if probeCountdown <= 0 { sensor.probe(); sensorAvailability = sensor.availability; probeCountdown = 90 } }`. Reset readFailures after each probe. While angles are nil in the active phase, also reset the sampler, or give `latest`, `velocity` and `stableDuration` an age limit, so stale samples cannot start or prolong a panic.
