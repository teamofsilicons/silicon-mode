# Review findings — mobile (confirmed by an adversarial verifier)

## 1. [medium] iOS signs into any account from an unsolicited ai.tos.mode://auth deep link (session fixation, one-tap sign-out)

**Verifier evidence:** Confirmed. `SiliconModeApp.swift:17` wires `.onOpenURL { store.handle(url: $0) }`. `AppStore.handle(url:)` (line 195) does `if SignIn.isAuthCallback(url) { Task { await completeSignIn(SignIn.parse(url)) } ; return }` and checks neither `isSigningIn` nor `auth`. `completeSignIn` then runs `case .session(let s): await client.adopt(s); signInError = nil; ... auth = .signedIn; await afterSignIn()`. Nothing validates the tokens first. `CellClient.adopt` overwrites the Keychain (`session = s; Keychain.save(s, Self.sessionAccount)`) and does not sign out the old session. `isAuthCallback` only checks the scheme and host. `web/public/auth/bounce.js` forwards any fragment (`location.replace(url)` with `url = TARGET + "#" + frag`). There is no apple-app-site-association, so `https://mode.teamofsilicons.com/auth/ios#access_token=...` opens in Safari, which asks "Open in Silicon Mode?", and one tap lets an attacker's session in. `afterSignIn` then runs `registerThisPhone()` in the attacker's account. With junk tokens, `client.user()` gets 401, `refreshed` fails with `.signedOut`, then `onSignedOut` runs `handleSignedOut`, and the victim's real Keychain session is already overwritten. Android has the guard this is missing: `SignIn.complete` checks `pendingSignInAt`, a 15-minute window, and validates with `cell.user(parsed.accessToken)`. The real iOS flow does not need onOpenURL, because `SignInView.signIn()` gets the URL back from `webAuth.authenticate(...)`. I lowered the severity from high to medium: it is a login-CSRF that needs the victim to tap a link and confirm Safari's prompt. The harm beyond the forced sign-out depends on social engineering, where the victim answers the attacker's look-alike Mac.

**Fix:** In `AppStore.handle(url:)`, ignore auth callbacks unless `isSigningIn == true && auth != .signedIn` and a sign-in nonce or timestamp was set in `SignInView.signIn()` within about the last 10 minutes. Better still, drop the auth branch from `onOpenURL` in release builds and keep it under `#if DEBUG` for the `SM_DEEPLINK` UI test. In `completeSignIn`, validate with `GET /auth/user` using the new token before `client.adopt(s)`. If a session already exists, refuse it, or confirm, then `await client.signOut()`, `realtime.stop()`, adopt, and `realtime.start()`. Do not show the `error_description` that comes from the URL.

## 2. [medium] Android sign-in sends bearer tokens to the hijackable custom scheme ai.tos.mode:// (App Link is not verified)

**Verifier evidence:** Confirmed. `web/public` has no `.well-known/` directory (`ls web/public/.well-known` gives No such file), and `docs/WEB.md:133` lists assetlinks.json under "Later". The `autoVerify` filter for `https://mode.teamofsilicons.com/auth/android` therefore never verifies, and on Android 12+ the cell's redirect loads `/auth/android` in the Custom Tab. `android.html` loads `bounce.js`, which runs `var TARGET = "ai.tos.mode://auth/callback"; ... location.replace(url)` with `#access_token=…&refresh_token=csr_…` attached. The manifest's custom-scheme filter (`<data android:scheme="ai.tos.mode" android:host="auth" android:path="/callback" />`) is not exclusive, so any app can declare it and Android will show a chooser or route the intent to that app. The tokens are final credentials: no code exchange or PKCE on the app side (`CallbackParser.parse` takes access and refresh tokens straight from the fragment). `docs/research/cells.md` says the Mac and iOS paths are safe because ASWebAuthenticationSession intercepts the hop, and names App Links as the primary Android path. That primary path is not deployed, so the fallback runs. The `pendingSignInAt` gate protects the real app from unsolicited callbacks, but it does not stop interception. Medium, because it needs a malicious app installed and the user (or a default) choosing it.

**Fix:** Publish `web/public/.well-known/assetlinks.json` (package `ai.tos.mode`, the release certificate's SHA-256, served as application/json) so the verified App Link delivers the fragment straight to MainActivity. In the Android-only bounce (android.html or a separate script, since bounce.js is shared with the ios, mac and app pages), navigate to `intent://auth/callback?<fragment params>#Intent;scheme=ai.tos.mode;package=ai.tos.mode;end` so Chrome only hands the tokens to the real package. `CallbackParser.parse` already reads `encodedQuery`.

## 3. [medium] iOS shows a reply box on questions the Mac marked unanswerable; the Mac rejects the answer and the card stays on "Sent" with the badge cleared

**Verifier evidence:** Confirmed. `SyncWire.questionRow` sends `options: q.answerable ? ... : []` and `allowText: q.answerable && q.allowsFreeText`. Unanswerable questions are common and are pushed. Examples are ClaudeCodeProvider's `title: "Waiting for you" ... answerable: false` and the transcript-derived permission prompts with `answerable: false`, which are all added in the `for q in s.pendingQuestions` push loop. iOS `QuestionCard.controls` renders `if question.allowText || question.options.isEmpty { replyField }`, so these cards get a text box. Android's card shows `"Answer this one on $macName."` here instead. `answer_question` never checks allow_text and inserts the row, so `r.ok` sets `.sent(...)`. The Mac's `CloudSync.handle` sets `if !q.answerable || !(optionOK || textOK) { outcome = .failed }` and only marks the question answered when `outcome == .applied`. iOS ignores its own answer's outcome in two places: in realtime `answers` with `if !mine, ...` (own answers skipped), and in `loadSelected`, where `ans.answeredBy == myDeviceID` gives `.sent(option:text:)` whatever `consumedAt/outcome` is. The card stays on "Sent · Waiting for <Mac> to pass it on" until the question is resolved on the Mac or expires. `pendingQuestionCount` only counts `.none, .failed`, so the badge clears. `answers.question_id` is `UNIQUE`, so no other phone or web client can answer afterwards. The same stuck state happens when an option answer comes back `failed` or `stale`.

**Fix:** In `QuestionCard.controls`, render `replyField` only when `question.allowText`. When `question.options.isEmpty && !question.allowText`, show `Text("Answer this one on \(macName).")` with no controls. In `loadSelected` and in the realtime `answers` handler (subscribe to UPDATE as well), when the answer is mine and `consumedAt != nil && outcome != "applied"`, set `questionUI[q.id] = .failed("\(macName) couldn't apply this answer — answer it on the Mac.")`, or a terminal closed state, so the badge and card show the agent is still waiting.

## 4. [low] Android: after a lost answer response, this phone's own applied answer is reported as "Someone got there first"

**Verifier evidence:** Confirmed. In `ModeRepository.answer`, `catch (e: CellException) { AnswerState.Failed(e.userMessage) }` runs even when the RPC committed server-side and only the response was lost (`execute` maps IOException to a NETWORK CellException). The realtime `answers` branch then does `val mine = answer.answeredBy != null && answer.answeredBy == prefs.phoneDeviceId ... if (mine || state is AnswerState.Sending || state is AnswerState.Sent) return`, so Failed stays. When the Mac applies the answer, the `questions` branch runs `if (_answers.value[question.id] !is AnswerState.Sent) { val outcome = ... AnswerState.Elsewhere(if (question.state == "resolved_on_mac") "mac" else null) ...`, which replaces Failed with Elsewhere(null). On a retry, `already_answered` falls into `else -> AnswerState.Elsewhere(...)`. The UI shows `"Answered elsewhere"` / `"Someone got there first."` (QuestionCard.kt:269-278) for an answer this phone sent. `loadFeed` keeps the card because `_answers.value[it.id] != null`. iOS handles `already_answered` by fetching the answer row. Low: the wrong label only appears after a lost response.

**Fix:** In the realtime `answers` branch, when `mine` and the state is null, `Failed` or `Sending`, set `AnswerState.Sent(label for answer.optionId ?: answer.text)` and call `retireQuestion`. In `answer()`, on `already_answered`, GET `answers?question_id=eq.<id>&select=option_id,text,answered_by,answered_from`. Map it to `Sent(label)` when `answered_by == phoneDeviceId`, and otherwise to `Elsewhere(answered_from)`. In the `questions` branch, do not overwrite the state when the answer row is this phone's.

## 5. [low] Android realtime never detects a silently dead socket and keeps showing "Live"

**Verifier evidence:** Confirmed. The realtime client is `http.newBuilder().readTimeout(0, TimeUnit.MILLISECONDS).build()`. The base client in ModeApplication sets connect, read and write timeouts but no `pingInterval`, so OkHttp sends no protocol pings and has no read deadline. The app pinger only writes (`ws.send(buildJsonObject { put("type", "ping"); ... })`), and `onFrame` ignores replies (`RealtimeFrame.Pong, RealtimeFrame.Other -> Unit`), so nothing measures time since the last frame. The loop blocks on `closed.join()`, which only completes from `onClosed` or `onFailure`. The `onAvailable` callback only completes `wake`, which nothing awaits while connected. `ModeRepository` only runs `refreshAll()` on a non-Live to Live transition or on `resync`. On a half-open TCP connection (server or load-balancer failover without FIN/RST, or a middlebox dropping state), sends are buffered until TCP retransmission gives up (about 15 minutes). `status` stays `Live` and no changes arrive the whole time. iOS cancels after `staleAfter = 70`. Low, because the socket is only held while the app is in the foreground (`onBackground` calls `release(HOLD_APP)`, which closes it, and `onForeground` calls `refreshAll()`), so it only affects a session where the app stays open the whole time. Android also destroys sockets when an interface goes away, which covers the plain Wi-Fi loss case.

**Fix:** Record `lastFrameAt = System.currentTimeMillis()` in `onFrame` for every frame, including Pong. In the pinger, call `ws.cancel()` when `System.currentTimeMillis() - lastFrameAt > 70_000`, so the loop reconnects and the Live transition triggers `refreshAll()`. Also add `.pingInterval(25, TimeUnit.SECONDS)` to the realtime OkHttpClient, so a missed protocol pong fails the socket.
