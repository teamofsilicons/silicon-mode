# Review findings — sync (confirmed by an adversarial verifier)

## 1. [high] Login CSRF: any web page or local process can sign the Mac into an attacker's account during the 10-minute sign-in window

**Verifier evidence:** Nothing ties a callback to this sign-in attempt. The only check is the state: AccountManager.handleCallback L187 `guard state == .signingIn else {...}` and complete L198 `guard state == .signingIn`, then `.tokens(let session)` runs `try await client.adopt(session)` (L226). CallbackPayload.parse (CellSession.swift L94-107) accepts any access_token/refresh_token pair, and signInURL (CellConfig L27-39) sends no state or nonce. The loopback page forwards whatever fragment it was opened with: `var frag = location.hash ...; fetch("/auth/complete", {... headers:{"X-Silicon-Mode":"__SECRET__"} ...})` (LoopbackPage L127-150). A top-level navigation from any tab to http://127.0.0.1:47291/auth/callback#access_token=<attacker>... therefore passes the Host check (`r.headers["host"] == "127.0.0.1:\(port)"`, L105) and the Origin and secret checks (L113-114), and the attacker's session gets adopted. The local vector is stronger than the finding says. Any local process of any uid can `GET /` (L109 serves the page, with pageSecret embedded, to anyone), copy the secret, and POST attacker tokens to /auth/complete without user interaction. It can poll the port to detect the window. The ai.tos.mode:// path is accepted while signingIn even when the loopback is in use. Impact is confirmed: CloudSync then pushes to the attacker's account, and CloudSync.handle → host.applyCloudAnswer → `m.hub.answer(q, with: a)` (CloudSync+AppModel L43-50) applies the attacker's option or free-text answers to the victim's agents. docs/BACKEND.md L60-62 says this exact attack is prevented. High severity is fair: the impact is remote approval of agent actions, but the attack needs the victim to be signing in (attack complexity high).

**Fix:** Bind tokens to the attempt. Preferred: ASWebAuthenticationSession with callback .customScheme("ai.tos.mode"), adopting tokens only from its completion handler, and have handleCallback/application(_:open:) ignore token-bearing URLs. If the loopback stays: do not serve the secret to arbitrary GETs. Generate a per-attempt nonce, pass it through the sign-in so it comes back in the redirect (or require a one-time path segment that only the browser URL the app opened knows), and reject /auth/complete without it. Accept ai.tos.mode:// callbacks only when this attempt used bounceRedirect. Before adopt+notify, fetch /auth/user with the received token in memory and show an in-app "Sign in as <name> (<id>)?" confirmation. Stop the listener after the first token-bearing POST.

## 2. [low] Loopback HTTP parser crashes the app on a negative Content-Length or a request target of "?"

**Verifier evidence:** LoopbackHTTPRequest.parse L197-202: `let length = Int(headers["content-length"] ?? "0") ?? 0` accepts -1, `guard buf.count - bodyStart >= length` passes, and `buf.subdata(in: bodyStart..<(bodyStart + length))` builds an inverted Range. For target "?", `target.split(separator: "?", maxSplits: 1)` returns [] and `parts[0]` traps. I compiled this exact function and ran both inputs: each exits with signal 5 (exit 133, a Swift trap). parse runs in receive() (L93) before the Host check in route, so any local process (any uid, since acceptLocalOnly only limits to local) can crash the app while the listener is up. Browsers cannot produce either request (they normalize "?" to "/?" and never send a negative Content-Length), so this is a local DoS limited to the sign-in window plus the 2 s retiring window. I downgraded it to low.

**Fix:** `guard let length = Int(headers["content-length"] ?? "0"), (0...256*1024).contains(length) else { return bad }`. Split with `omittingEmptySubsequences: false` and require `parts.first?.hasPrefix("/") == true`. Make parse return incomplete/bad/request so receive() can answer 400 and close the connection instead of trapping.

## 3. [medium] Full project paths leave the Mac in provider_session_id (Aider always, Kiro fallback); the privacy guarantee is violated

**Verifier evidence:** SyncWire.sessionRow L235-239: `let native = String(s.nativeID.prefix(200))` … `providerSessionID: native`. The value is neither redacted nor reduced to ~. AiderProvider.parse L84: `ParsedSession(nativeID: "\(cwd)#\(Int(started?.timeIntervalSince1970 ?? 0))"` with cwd = MoreFiles.gitRoot(...) (L21/L27). FileSessionScanner.assemble passes it through unchanged (MoreProviders.swift L769 `AgentSession(provider: provider, nativeID: s.nativeID`). KiroProvider.readClassic L103: `j["conversation_id"].text ?? "cwd:\(cwd)"`. push_batch stores x.provider_session_id verbatim (0001_init.sql L200-205). This contradicts CloudSync L42 "never sends cwd paths" and the sessionRow comment at L232. The grapheme-vs-code-point point is also correct: `prefix(200)` counts Characters while the CHECK is char_length ≤ 200, and a failing session row is rebuilt on every batch (never confirmed). Option labels are also sent unredacted (`label: o.label.clippedScalars(120)`, L275).

**Fix:** Derive the UUID from the full s.nativeID and send an opaque provider_session_id, e.g. `"h:" + sha256Hex(s.nativeID).prefix(62)` for any id containing "/" (or hash every provider's id), otherwise `s.nativeID.clippedScalars(200)`. Pass option labels through SyncRedactor.clean.

## 4. [medium] SyncRedactor misses common secret shapes, so credentials in commands reach the cloud in event summaries and question bodies

**Verifier evidence:** I compiled the exact `specs` from SyncWire.swift L334-345 with NSRegularExpression and ran them. These inputs come through UNCHANGED: `psql postgres://admin:S3cretPassw0rd@prod-db:5432/app`, `export DATABASE_URL=postgres://admin:S3cretPassw0rd@db/app`, `curl ... -u sk_live_51HxAbCd...` (the rule is `\b(sk|pk|rk)-...` with a hyphen, but Stripe uses sk_), `curl -d '{"password":"hunter2hunter2"}'` (the closing quote blocks `(\s*[=:]\s*)`), `mysql --password hunter2hunter2`, `git clone https://oauth2:glpat-...@gitlab.com/...`, and `Authorization: Basic YWRt...`. Only `export API_KEY=...` was redacted. These strings reach the cell through SyncMapper.eventSummary (L267-270) and questionRow body `q.detail.map { SyncRedactor.clean($0).clippedScalars(8000) }` (L284). The redactor's own doc says it covers `password=…`-style secrets and API keys, so these are concrete gaps in common forms.

**Fix:** Add rules before the generic key=value rule. URL userinfo: `(?i)\b([a-z][a-z0-9+.-]*://)[^/\s:@]+:[^/\s@]+@` → `$1•••@`. Stripe: `\b(sk|rk|pk)_(live|test)_[A-Za-z0-9]{16,}`. Basic auth: `(?i)\b(basic)\s+[A-Za-z0-9+/=]{12,}` → `$1 •••`. Quoted JSON keys: `(["'])([A-Za-z0-9_-]*(password|passwd|secret|token|api[_-]?key|access[_-]?key))\1\s*:\s*("[^"]*"|'[^']*'|[^\s,}]+)`. CLI flags: `(?i)(--?(password|passwd|token|secret|api-key)[ =])\S+`. Plus glpat-, npm_ and hf_ prefixes. Add unit tests built from these inputs.

## 5. [low] Signing in again right after Sign out: the old sign-out task revokes and wipes the new session, and sync stays suspended

**Verifier evidence:** AccountManager.signOut L164-176 sets `account = nil; state = .signedOut` synchronously, then `Task { if had, let hook { await hook() }; await client.signOut(); if had { notify(false) } }`. goOffline (CloudSync L220-229) sets `suspended = true` and awaits the offline push (deadline 3 s, but `await push.value` also waits on any in-flight refresh Task, because CellClient.refresh awaits an unstructured task). CellClient.signOut L238-243 reads the token at call time, `restore()?.session.accessToken`, then calls clear(). If a new sign-in completes in the window, complete() runs `client.adopt(new)`. notify(true) → reevaluate L139-147: same user, running → no-op, so `suspended` stays true. The old task then revokes the new token and clears the Keychain. notify(false) → reevaluate sees account != nil → no-op. requestFlush (L266) returns while suspended, and handleFailure swallows .notSignedIn (L363-364). clear() does not call endedHandler (only end() does), so the UI keeps showing signed in. The same suspended-forever result happens when adopt lands after clear() but before notify(false). The bug is real, but the window is normally ~1 s (two quick RTTs) while a browser sign-in takes longer. It is likely only on slow networks, so low.

**Fix:** Have the sign-out task target its own session: capture `let ending = await client.session` before the hook, POST with that token, and clear() only if the stored refresh token still equals ending.refreshToken. Add a .signingOut state that blocks signIn() until the task finishes. In CloudSync, reset `suspended = false` in start() and when the observer reports signed-in for a running sync, and treat .notSignedIn while account.isSignedIn as a session loss rather than returning silently.

## 6. [medium] Transient auth or proxy errors count as "poison" and discard queued events, question resolutions and consumed reports within about 15 s

**Verifier evidence:** handleFailure L375-392 counts every non-retryable CellError, from either ensureDevice() or push_batch, and after 3 of them runs `l.outbox.removeAll(); for k in l.pendingUpdates.keys { l.close(question: k) }; l.pendingUpdates.removeAll(); l.pendingConsumed.removeAll()`. isRetryable (CellClient L27-33) excludes 409, 403, 404 and .decoding. refresh() (L149-159) retries 409 only while `attempt < 3` (about 2.4 s), then `default: throw e`. So a refresh_in_progress lasting through three flushes (backoff 2/4/8 s), a register_device decoding failure, or a proxy or WAF 403/404 is counted as payload poison. Closed questions go into closedQuestions, so their resolved_on_mac/answered updates are never sent, and the server rows stay `pending` until expires_at (24 h). Answered on the phone, they come back `stale`. pendingConsumed recovers (re-delivered answers hit hasHandled → reported stale), but with the wrong outcome. The wipe also never removes real poison rows: session rows are rebuilt each batch because `prev == nil` (not confirmed), and questions are re-added because c.questions only commits on success. A bad session row (e.g. the provider_session_id char_length violation) therefore wedges sync forever.

**Fix:** Count poison only for push_batch responses carrying a data SQLSTATE (class 22, class 23 except 23503, or 21000). Treat 409/refresh_in_progress, refresh/register decoding failures and 403/404/413 without a PostgREST code as transient. When poison is confirmed, bisect by component (sessions, events, questions, usage) and blacklist only the offending session or question id instead of wiping the outbox, pendingUpdates and pendingConsumed.

## 7. [medium] Position-based AgentEvent ids break the sync ledger's dedupe: Kiro events stop syncing after 12 turns, Aider events are duplicated or dropped

**Verifier evidence:** CloudSync dedupes only by id: `let seen = Set(l.seqs[row.id]?.seen ?? []); let fresh = s.recentEvents.filter { !seen.contains($0.id) }` (L495-496), and SyncLedger.enqueue also skips seen ids. EventList.add builds ids as `"\(prefix):\(id)"` (MoreProviders L483-485). KiroProvider.readClassic L106: `for (i, entry) in j["history"].array.suffix(12).enumerated()` → `events.add("\(i).u", ...)`, so with 12 or more entries the newest turn is always `11.u`/`11.a`, ids that are already seen, and new turns are never pushed. Aider L45/L63-70: `MoreFiles.tailLines(path, maxBytes: 128 << 10)` then `events.add("u\(i)", ...)`. tailLines (L220-230) slides the window and drops the first partial line, so once the file exceeds 128 KB the indices shift on every append: old lines get unseen ids and are re-pushed with new seqs, and new lines that land on previously seen ids are dropped. Kiro's new jsonl parser has the same problem (`for (i, line) in MoreFiles.tailLines(path, maxBytes: 384 << 10).enumerated()`, L59). Omni falls back to `UUID().uuidString` when seq is missing (L127).

**Fix:** Use stable ids. Kiro classic: absolute history index (`let h = j["history"].array; for i in h.indices.suffix(12)`). Aider and Kiro jsonl: have tailLines return the window's start byte offset and use the absolute offset of each line as the id. Omni: hash the raw line instead of UUID() when seq is missing.

## 8. [low] One ledger file shared by all accounts: switching accounts and back resets seqs, so new events are deleted by push_batch's tail trim and ghost sessions remain

**Verifier evidence:** There is one file (CloudSync init L119, `cloud-sync.json`), and SyncLedgerStore.load L122-126 returns `SyncLedger(deviceID: deviceID)` when `l.deviceID != deviceID`. start() L190-195 reuses `defaults.string(forKey: Keys.device(user.uuid))`, so after A → B → A, dA is reused with an empty ledger and seqs restart at 1. For a session S (deterministic UUIDv5, so the same row) whose server events reach seq N, push_batch inserts seq 1..k `ON CONFLICT (session_id, seq) DO NOTHING`, then `DELETE ... WHERE ev.seq <= m.top - tail` (0001_init.sql L219-224) deletes them immediately while N-30 ≥ k. Nothing else deletes or splits the ledger (ledgerStore.delete is never called). The empty `live` and `pushedQuestions` maps also mean that sessions and questions A left live are never ended or resolved. Real, but it needs an account switch and back while sessions with server history are still active, so low.

**Fix:** Store ledgers per device id (e.g. `cloud-sync-<deviceID>.json` or a `[deviceID: SyncLedger]` map). As a fallback, when creating a fresh ledger for a device id that already existed, seed `seqs[session].next` from the server's max(seq) for that session before enqueuing.

## 9. [low] Claude Code "Waiting for you" placeholder reuses one question id per session, so later waits never reach phone/web

**Verifier evidence:** ClaudeCodeProvider.derive L183-187: when reg.status == "waiting", no open questions, no open tool (permissionPlaceholder returns nil, L629) and waitingFor != "dialog open", it emits `AgentQuestion(id: "\(sessionRef):waiting", ...)`, the same id for every wait in that session. After the first wait ends, buildBatch L535-538 queues resolved_on_mac and apply L612-614 calls `l.close(question:)`. On the next wait, L524-525 `guard l.pushedQuestions[row.id] == nil, l.pendingUpdates[row.id] == nil, !l.closedQuestions.contains(row.id) else { continue }` skips it. Even after it leaves the 300-entry closedQuestions, the server's `ON CONFLICT (id) DO NOTHING` (0001_init.sql L246) keeps the row resolved. Impact is limited: the session row still shows state waiting / waiting_reason, and the placeholder is answerable:false. So it is low.

**Fix:** Make the id unique per wait, e.g. `"\(sessionRef):waiting:\(Int((reg.statusUpdatedAt ?? now).timeIntervalSince1970))"`.

## 10. [low] Sign-out with an expired access token leaves the server session alive

**Verifier evidence:** CellClient.signOut L238-243: `if let token = restore()?.session.accessToken { _ = try? await raw("POST", "auth/sign-out", ..., token: token) }; clear()`. There is no needsRefresh check, the result is ignored, and there is no 401→refresh retry. The only thing that refreshes first is the willSignOut hook (goOffline → pushOffline → client.rpc → accessToken()), and it returns early when CloudSync is not running (`guard running, let dev = deviceID, ...`, L221). That happens when the user turned cloud sync off (ModeSettings default is true) or the device never registered. In that state nothing refreshes after launch (only restore()'s fetchUser), so after more than 30 minutes (access token lifetime ≤ 30 min, docs/BACKEND.md) the sign-out POST carries an expired JWT, gets rejected, and the error is swallowed. The local pair is wiped and the server session is never revoked. Low impact, since the refresh token no longer exists locally, but a session revocation the user asked for does not happen.

**Fix:** In signOut: `let token = try? await accessToken()` (refreshes if needed). If the POST returns 401, call refreshAfterRejection(of:) and retry once, then clear(). Optionally surface a failure to revoke.
