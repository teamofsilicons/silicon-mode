# Review findings — providers (confirmed by an adversarial verifier)

## 1. [high] FileSessionScanner keys WAL SQLite stores by the main-file stamp, so Crush/Cursor state freezes mid-turn and can show a false 'needs you'

**Verifier evidence:** Confirmed. MoreProviders.swift:709-715 keys the cache on the main file only: `guard let st = FileStamp.of(f) else { continue }` ... `if let c = parsed.current[f], c.0 == st { if let s = c.1 { sessions.append(s) }; continue }`. CrushProvider.swift:26 (`scanner.scan(files: dbs.sorted(), ...)` with `crush.db`) and CursorProvider.swift:31 (`store.db`) send SQLite files through this path. A WAL-aware helper already exists and is ignored here: `FileStamp.sqlite` (MoreProviders.swift:192, 'Combined stamp of a SQLite db and its -wal'). The parsers do use it (`let mtime = FileStamp.sqlite(db)?.date` at Crush:56 and Cursor:61). SQLiteReader opens with `mode=ro` and reads WAL content (or a copy that includes the -wal), so a re-parse would see the new rows, but no re-parse happens. Crush sets `PRAGMA journal_mode = WAL`, so commits go to crush.db-wal. The main file changes only on an auto-checkpoint (about 1000 pages, usually during heavy streaming writes) or when crush exits. Whatever state was cached at the last mid-turn checkpoint therefore stays after the turn ends. With cached `.toolPending`, `MoreState.derive` returns `.working` whatever the quiet time (`case .toolPending: return .working`). `maybeWaiting` (`guard alive, activity == .toolPending, cpuActive == false, ctx.now.timeIntervalSince(lastActivity) >= after`) then adds the 'may be waiting for approval' question, and assemble sets `state = .needsYou`. With cached `.running`, the session shows working until idleAfter (10 min, AgentProvider.swift:38). The horizon check `ctx.now.timeIntervalSince(st.date) > horizon` also uses the stale main-file mtime. The stale state clears only at the next checkpoint or when crush exits (close checkpoints and deletes the WAL).

**Fix:** In FileSessionScanner.scan, take the stamp from the db plus its -wal for SQLite stores, and use it for both the cache key and the horizon check. Add a parameter `stamp: (String) -> FileStamp? = FileStamp.of` to scan(), replace line 709 with `guard let st = stamp(f) else { continue }`, and pass `stamp: FileStamp.sqlite` from CrushProvider.scan and CursorProvider.scan. Alternatively, pick FileStamp.sqlite automatically when the path ends in .db, .sqlite or .sqlite3.

## 2. [high] CLI agents started in an editor's integrated terminal are dropped as 'IDE features', so they show finished or are missing while they work

**Verifier evidence:** Confirmed. ProcessFallbackSupport.swift:249-256: `let attributedElsewhere = idx.tree.ancestors(of: pid).contains { a in switch idx.roles[a.pid] { case .agent?, .orchestrator?: true; case .ide?: !allowIDE; case nil: false } }; if attributedElsewhere { continue }`. classify() (lines 131-135) marks any process whose path or argv contains `/Visual Studio Code.app/`, `/Cursor.app/Contents/`, `/Windsurf.app/Contents/`, `/Kiro.app/Contents/` or `/Zed.app/Contents/` as `.ide`. That includes VS Code's or Cursor's pty host (`.../Code Helper.app/...`, which is under `/Visual Studio Code.app/`), the direct parent of an integrated-terminal shell. Nothing in the module passes `allowIDE: true` (grep finds only the default parameter). So `gemini` → zsh → Code Helper(ptyHost) is skipped. With no procs, FileSessionScanner uses horizon = activeWindow and assemble has alive == false, and `MoreState.derive` returns `.finished` (`if !alive { ... return .finished }`) while Gemini is working. Other consequences: Aider returns nothing (`guard !procs.isEmpty else { return [] }`, AiderProvider:17). Crush loses live-cwd DB discovery (Crush:19). ProcessFallbackProvider:27 emits nothing. CopilotProvider:22-25 skips the whole session dir when the `inuse.<pid>.lock` pid has any `.ide` ancestor, including a copilot CLI run in the VS Code terminal. The research note (agents-more.md:416) only meant to exclude editor-hosted runtimes such as `copilot-runtime --headless --stdio`. The core providers (Claude Code, Codex) use their own CoreProcess matching and are not affected.

**Fix:** Treat an `.ide` ancestor as the owner only when no interactive shell lies between it and the agent: `var viaShell = false; let attributedElsewhere = idx.tree.ancestors(of: pid).contains { a in if ["zsh","bash","fish","sh","dash","tcsh","nu","login","tmux","screen"].contains(a.exeBase) { viaShell = true }; switch idx.roles[a.pid] { case .agent?, .orchestrator?: return true; case .ide?: return !allowIDE && !viaShell; case nil: return false } }`. Apply the same shell-in-between rule to CopilotProvider's `ideHosted` check. Editor-hosted runtimes spawned directly by the extension host, with no shell in between, stay excluded.

## 3. [low] OpenClaw keeps cached `running` sessions forever when sessions.list fails or the CLI briefly goes missing

**Verifier evidence:** Confirmed in code, but I downgraded the severity because it needs a failure or reinstall window. scan() renders `snapshot.sessions` from the last successful fetch with `var st: AgentState = s.running ? .working : ...`. The age filter skips running sessions: `if !s.running, mine.isEmpty, quiet > ctx.activeWindow { continue }`. On a failed call, fetchSessions returns without touching `sessions`: `guard let out = await env.run(...), out.status == 0, let j = Self.parseJSON(out.stdout) else { return }`. A missing CLI latches: `guard let exe = env.which("openclaw") else { state.withLock { $0.cliMissing = true }; return }`, and scheduleFetchIfNeeded then refuses forever: `guard !s.inFlight, !s.cliMissing else { return false }`. `which` uses `fm.isExecutableFile`, which is false for a dangling symlink, and that state can occur during an `npm i -g openclaw` upgrade. A single unlucky fetch then freezes the session list until the app restarts, and a session that was `hasActiveRun` shows 'working' for as long as any gateway process exists. For non-latched failures (timeout or auth), retries keep running every 15 s because cached running sessions count as `busy`, so the stale state lasts only as long as the failure. Approvals are unaffected because they come from the DB.

**Fix:** Add `lastSuccess: Date` to State and set it only after a successful parse in fetchSessions. In scan, when `ctx.now - lastSuccess > 2 * busyInterval + 15`, treat the cached sessions as stale: clear `running` and derive finished/idle from updatedAt, or drop them. Replace the `cliMissing` latch with `cliMissingAt: Date?` and retry `env.which` after about 60 s instead of refusing forever.

## 4. [medium] AgentHub.refresh runs re-entrantly, so overlapping refreshes overwrite newer snapshots with older ones (questions flicker, alert sound replays) and pile up scans

**Verifier evidence:** Confirmed. AgentHub is an actor, and refresh() suspends at `let all = await withTaskGroup(...)`, so actor reentrancy allows overlapping calls. It ends with an unconditional `latest = Snapshot(sessions: merged, counts: AgentCounts(merged), takenAt: ctx.now); return latest`, with no ordering check. AppModel.refreshAgents also applies whatever comes back: `let snap = await hub.refresh() ... if snap != snapshot { let hadQuestions = Set(snapshot.pendingQuestions.map(\.id)); snapshot = snap; let newQuestions = ...; if !newQuestions.isEmpty, ... { sounds.play(.question) }; cloud.agentsChanged() }`. Overlap is routine. There is the 2 s poll loop, answer() calls `try await hub.answer(q, with: a); await refreshAgents()` (hub.answer can run while a poll refresh is suspended), and refreshAgentsSoon clears its guard before awaiting: `try? await Task.sleep(for: .milliseconds(150)); refreshScheduled = false; await refreshAgents()`. A burst of hook events can therefore start a new full refresh (ProcessTable.snapshot plus every provider) every 150 ms while earlier ones are still running. When a poll refresh R1 has already scanned Claude Code with Q pending and is still waiting on a slower provider, and the user's answer triggers R2, R2 can finish first. AppModel then applies R1 last, Q reappears, `newQuestions` contains Q again, and the question sound plus the cloud sync fire for an answered question until the next poll removes it.

**Fix:** In AgentHub, store `latest` only when the result is newer: `if ctx.now >= latest.takenAt { latest = Snapshot(...) }; return latest`. Better, coalesce: keep `private var inFlight: Task<Snapshot, Never>?` plus a `dirty` flag, let callers await the in-flight task, and run at most one follow-up refresh. In AppModel.refreshAgents, `guard snap.takenAt >= snapshot.takenAt else { return }`. In refreshAgentsSoon, reset `refreshScheduled = false` only after `await refreshAgents()` returns.

## 5. [medium] opencode legacy scan caches the derived state (liveness and time decay) by session-file mtime, so 'working'/'finished' freezes

**Verifier evidence:** Confirmed. OpenCodeProvider.swift:259-266: `guard let st = CoreFS.stat(p), st.mtime >= since else { continue }; if let cached = c.legacy[p], cached.mtime == st.mtime { if let s = cached.session { out.append(s) }; continue }`. The cached value is a fully derived AgentSession from legacySession, which bakes in liveness at cache time (`let live = cwd.map { liveCwds.contains($0) } ?? false`), the newest message file at cache time, and the clock-based decay (`if state == .finished, ctx.now.timeIntervalSince(updated) > ctx.idleAfter { state = .idle }`). Only the session JSON's mtime is checked, not `storage/message/<id>/`. Example: a prompt touches the session file, a scan caches `.working` (live, newest message incomplete), then the user presses Ctrl-C. The process is gone and the session file never changes again, so 'working' is shown until the mtime falls out of the 30-min window. A cached `.finished` never decays to idle. legacyScan runs whenever svc is nil (no service.json, dead service pid) or the service request failed (`downUntil`), so it is reachable. `c.legacy` is also never pruned.

**Fix:** Cache only the parsed file facts (id, cwd, title, created/updated, newest message role/completed/error), keyed by the session-file mtime combined with the mtime of `storage/message/<id>` (the directory mtime changes when message files are added; also stat the newest message file). On every scan, compute `live` from the current `liveCwds`, the state, and the `ctx.now` idle decay. After the loop, prune `c.legacy` to the paths visited in this scan.
